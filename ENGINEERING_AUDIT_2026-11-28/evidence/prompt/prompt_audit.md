## 3. Findings

### P-01 Server AI path is told to deliver multi-part replies or a downloadable file, which it cannot do
- Severity: Critical. Classification: Confirmed bug.
- Location: canvas_prompt.py:1411-1417 (MULTI-PART), 1636-1644 (`scope`), 1818-1840 (file contract); routes.py:1039-1045; ai_client.py:43-61; main.js:198,210 (`m.file = true` is sent to `/canvas/ai-generate`).
- Quoted text:
  - "MULTI-PART REPLIES: if the complete design will not fit in one reply, split it … the user answers "continue" for the next part."
  - "Use your code / file tool: write a short script that BUILDS the design … Do NOT paste the JSON in the chat."
- Evidence:
  - With `machine={'file':True}`, `build_prompt` contains "Use your code / file tool" (True).
  - The server makes one text-only call with no tools and no follow-up turn.
  - Compiling `EXAMPLE` + `"part":{"index":1,"of":2}` gives `PART_MISSING: … In the AI chat, reply "continue"…`. The `aiFixLoop` then sends that error to the AI as a repair problem, which the server model cannot resolve.
- Impact: Large designs on `/canvas/ai-generate` come back as part 1 only, which is a guaranteed failure. When "AI delivers a .json file" is ticked, Claude or Gemini is asked to use tools it does not have.
- Proposed instruction: add a `server=True` flag to `build_prompt`/`build_repair_prompt` that uses this contract:
  > "Reply with the complete design as one JSON object and nothing else. You have exactly one reply: there is no 'continue'. If the design would exceed about 250 boards, use repeat / radial / morph / mirror / assemblies to keep it under that, and never split it into parts."

  Strip `file` from `machine` in `/canvas/ai-generate` and `/canvas/ai-fix`.

### P-02 A truncated LLM reply is accepted silently
- Severity: High. Classification: Confirmed bug (client). The resulting failure is shown to the user as an LLM failure.
- Location: ai_client.py:46 (`maxOutputTokens: 65536`), :57-60 (only an empty reply is rejected), :73 (`max_tokens=64000`), :89-90.
- Evidence: `finishReason` (`MAX_TOKENS`) and `stop_reason == 'max_tokens'` are never checked when some text was returned. Truncated JSON then becomes `JSON_SYNTAX`, and the repair prompt asks the model to re-emit the whole design, which truncates again.
- Potential, needs testing: Gemini 2.5 thinking tokens and Claude `effort: xhigh` thinking count against these limits.
- Proposed fix: treat truncation as `AIError('reply was cut off at the output limit; simplify or use generators')`. Add to the prompt: "Your reply has a hard limit of about 40,000 tokens including the plan; keep the plan under 60 short lines."

### P-03 Output-format contradictions (fence vs JSON MIME type, "in your head" vs a written plan)
- Severity: Medium. Classification: Prompt engineering issue.
- Location:
  - canvas_prompt.py:1402: "Reply with exactly ONE ```json code block"
  - L1369 (spec): "Return **one** fenced ```json code block"
  - L1424 FINAL_REMINDER, and Instruction 11 (L1997)
  - ai_client.py:46: `'responseMimeType': 'application/json'`
  - L1427-1428: "do the work in your head; the only output is the JSON", while Instruction 2 requires a large written `plan`.
- Evidence: The output-format rule is stated 4 times. Gemini's JSON mode cannot emit a fence, and `_extract` (canvas.py:99-107) falls back to the raw text, so normal output parses.
- Potential, needs testing: Gemini may return the fenced text as a JSON string (`"```json\n{…}"`). `_extract` would then cut at the first `{` and keep the escaped quotes, which gives a syntax error.
- Proposed instruction: state the format once, per provider. Server/Gemini: "Your reply is parsed as JSON: output the bare object, no fences." Copy-paste: keep the fence. Drop "in your head", or make the plan optional (P-04).

### P-04 The "plan" is mandatory, large, and ignored by the compiler
- Severity: Medium. Classification: Prompt engineering issue.
- Location: canvas_prompt.py:991-993 ("the compiler ignores it"), Instruction 2 (L1930-1950), DESIGN_TEAM (L1427-1446), PRECISION 8, IMAGE_SPEC 4/10/11, `hard_constraints` ("tick every one off in "plan.checks"").
- Evidence:
  - `grep plan board_engine/*.py`: plan is only touched in canvas.py:233-241, where multi-part plan lists are merged.
  - Plan sub-keys `audit`, `checks`, `concept`, `datums`, `reference` are consumed nowhere.
  - The plan's own example (L1115-1160) omits `steps` and `economy`, which ASSEMBLY ORDER and DESIGN_QUALITY require.
  - The field list repeats `"reference"?` twice (L991-992).
  - SUCCESS_CRITERIA (L1448) says "the compiler measures every one of these … every inventory item present". The compiler cannot see the inventory.
- Impact: Thousands of output tokens of self-assessment ("SCORE the design 1-5", "audit 10 boards", one line per inventory item) are spent with no check. This competes with the board JSON for the output budget (P-02) and gives a false sense of verification.
- Proposed instruction:
  > "Optional `plan.parts`: a list of the product's components with counts, e.g. "wing x2, tailplane x1, fin x1, canopy x1"; at most 40 lines. Do not write audits, scores or check lists."

  Either make the compiler compare `plan.parts` counts against groups/ids (Enhancement), or remove the claim "the compiler measures every one of these".

### P-05 `hard_constraints()` mislabels and drops dimensions
- Severity: High. Classification: Confirmed bug (prompt generator).
- Location: canvas_prompt.py:2056-2090.
- Evidence (scratch run):
  - "1200 x 600 x 750 mm desk, 18 mm plywood" gives "- x: 750 mm" and "- a size: 18 mm". 1200 and 600 are lost, "x" (the length axis) is set to the height, and the thickness becomes a size.
  - "A 200 mm long … toy car" gives "- A: 200 mm".
  - "simple realistic boat" gives "detail level: 5".
- Impact: The model is handed a wrong HARD CONSTRAINT that contradicts the user's intent and the compiler's own `L x D x H` rule (spec L1272-1273).
- Proposed fix: parse `a x b x c unit` as "length a, depth b, height c". Skip numbers followed by a material word (thickness). Use the word after the number as the label ("200 mm long" → length). When both "simple" and "realistic" appear, emit nothing.

### P-06 Requirements are not passed on the server fix path
- Severity: Medium. Classification: Confirmed bug.
- Location: routes.py:762 (`/canvas/repair-prompt`) and :1060 (`/canvas/ai-fix`) call `compile_source` without `requirements=`. `/canvas/compile` (:848) does pass them.
- Impact: A `REQUIREMENT_MISMATCH` error seen in the UI (main.js:579 passes requirements) never reaches the repair prompt. `/ai-fix` can even return `changed:false` ("no errors"), which ends the loop with "The AI could not fix every problem".
- Fix: pass `requirements=_requirements(data)` in both routes, and send it from `aiFixLoop`.

### P-07 Curve guidance contradicts itself (spline and superellipse vs dense polygons)
- Severity: Medium. Classification: Prompt engineering issue (introduced by the diff).
- Location:
  - L921: "6-12 points make any organic outline … instead of 40-100 polygon points"
  - L1519: "compute the points from the curve … every 5-10 degrees or 5-20 mm" (PRECISION 5, which also gives a 24-point superellipse worked by hand at L1523-1527)
  - L1782 (IMAGE_SPEC 5): "polygon / path points … about every 5% of length along curves"
- Impact: The model gets three incompatible strategies. The hand-computed one (24 points per rib) is the most token-expensive and error-prone, and it ignores the native `superellipse`.
- Proposed instruction (replace PRECISION 5 and IMAGE_SPEC 5):
  > "Curves: use `superellipse` for rounded sections, `spline` through 6–12 measured points for free outlines (mark tab edges with two `corners`), `arch`/`arc` for circular arcs. Use explicit polygons only for faceted shapes. Parts that rest on each other use the same points."

### P-08 Construction advice that the compiler rejects (cross-lapped silhouettes, stacked discs)
- Severity: High. Classification: Prompt engineering issue.
- Location:
  - L1101: "a tree or bush = a few interlocking silhouette boards (cross_lap them for volume)"
  - L1565: "ROUND AND CYLINDRICAL PARTS … stacked discs, cross-lapped pairs"
  - DESIGN_QUALITY L1457-1458: "waffle / egg-crate frames, stacked contour slices"
  - L1232 ladder 5: "double it with a crossing piece (cross_lap)"
- Evidence:
  - `probe.out`: a profiled fuselage cross_lapped with a profiled wing gives `JOINT_NEEDS_PLAIN_BOARD … 'FUS' has a profile` (canvas.py:1567-1568).
  - With `"auto"`: `UNATTACHED_BOARD`.
  - `probe3.out`: stacked discs with tab_slot give `NO_CONTACT`; with auto, `NOT_JOINED`.
- Impact: The prompt recommends exactly these techniques for organic and round objects, and each one fails to compile.
- Proposed instruction:
  > "cross_lap only joins two PLAIN rectangles. Silhouettes, discs and ribs (anything with a profile) are joined by tab_slot along a straight edge onto a plain board. Never stack boards face to face. A round solid is radial fins on a hub, or ribs on a plain spine."

### P-09 Missing capability: slotted profiled cross-halving (the standard laser-kit joint for aircraft, animals and trees)
- Severity: High. Classification: Missing capability.
- Evidence: Same probe as P-08. A profiled fuselage and wing cannot cross unless both are plain rectangles. An aeroplane can only be built as ribs on a keel, plus wings tabbed onto a fuselage side.
- Impact: For "Aeroplane" the most natural flat-pack construction is impossible, and the prompt does not say so in its "cannot build" list (L1240-1251).
- Proposed: either implement cross_lap for profiled boards (notch along the crossing line, with a check that both outlines are solid there), or add to "What this generator cannot build": "Two shaped boards slotted through each other (a wing through a fuselage profile): use a plain rectangular core where they cross, or tab one onto the other's face."

### P-10 "0 warnings" cannot be met when following the prompt's own generator example, and the 5 mm threshold disagrees with the message
- Severity: Medium. Classification: Confirmed bug (compiler message and prompt mismatch).
- Location:
  - inspection.py:34 (`STEP = 5.0`), :191 (`TOUCH < d <= STEP` reports 5.0 mm). The message says "make the offset deliberate: >= 5 mm".
  - Prompt L1283: "clearly offset (>= 5 mm)"
  - SUCCESS_CRITERIA L1449: "0 errors and 0 warnings"
  - Repair rule 1 (L2119): "Fix every [WARNING] too"
- Evidence (`probe2.out`):
  - The prompt's morph RIB example on a keel compiles with 0 errors but gives `MISMATCHED_PAIR` ×2 (morph rounding makes "twins" differ by 1–4 mm) and `MISALIGNED` ×3, two of them at exactly 5.0 mm.
  - 4 radial blades on a hub give 4 × `MISALIGNED` "5.0 mm apart … (>= 5 mm)".
- Impact: The repair loop keeps "fixing" artifacts of the compiler's own generators and invites regressions.
- Fix: use `d < STEP` (or say "> 5 mm"), and exempt generated copies of one morph/radial from the twin and flush checks. Prompt: "Warnings on copies generated by morph/radial may be left."
